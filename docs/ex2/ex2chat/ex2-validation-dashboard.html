Design philosophy

Every architectural decision was made to be defensible in an interview. The schema uses fully normalized sub-tables (not JSONB) because Ex4 will need to query by skill or year. Applications are a separate table because the relationship carries its own status. PKs are strings (cv_001, job_001) because they exist in the source data, avoiding a legacy mapping table.

Schema Design & Decisions

The schema uses fully normalized sub-tables (not JSONB), natural string PKs (cv_001, job_001), and explicit sort_order to maintain document order. Every design choice is justified by future exercises.

Core Entities

1. CANDIDATES (normalized)

Why normalized, not JSONB? Ex4 needs to search by skill name, by experience years, by language proficiency. These queries are fast on normalized tables with proper indexes. JSONB blocks them.
-- Fast (normalized): SELECT candidates.* FROM candidates JOIN candidate_skills ON candidates.id = candidate_skills.candidate_id WHERE candidate_skills.name = 'Python' -- Slow or blocked (JSONB): SELECT * FROM candidates WHERE skills @> '[{"name":"Python"}]' -- Can't index into array efficiently

2. APPLICATIONS (the join table with status)

Why a separate table? Status is a property of the pair (candidate for position), not of either alone. Abel McKinney is Rejected for job 9, Waiting for job 1. The join table is the only place to put this without denormalization.

3. sort_order on every sub-list

Why not insertion order? The seed script is idempotent — re-running it should produce the same database. Without sort_order, re-seeding changes the result order (insertion order is unstable). With sort_order, the author's intended order is preserved.

Key decisions you should be able to defend

  • Natural PKs (cv_001): These exist in source data; using them avoids a legacy mapping table. UUIDs deferred to Ex3+ when records are created via API.
  • Fully normalized sub-tables: Ex4 requires WHERE skill.name = 'Python'. JSONB blocks this. Join cost at read time is cheaper than losing query capability.
  • sort_order INT: Maintains document order independent of insertion order. Seed script is idempotent.
  • highlights TEXT[]: Bullets are display-only, never filtered. Array is fine; don't create a 6th join table.
  • applications as a join table: Status is a relationship property, not a field on either entity. The join table is the only correct place.
  • users standalone (no FK): Auth is infrastructure. Audit trails belong in Ex6, not here.

Known Gaps & Mitigation

Two intentional gaps, both marked for Ex3. These are not bugs; they are conscious scope decisions.

Gap 1: created_at type annotation

Issue: In models.py, created_at: Mapped[Optional[str]] is annotated as string, but the schema serializes it correctly as ISO-8601 datetime string in JSON responses.

Impact: Zero at runtime. Type checkers will complain. The API response is correct.

Fix: Ex3 first commit: change to created_at: Mapped[datetime] and handle serialization in Pydantic schema.

Gap 2: db.test.ts skipped

Issue: The Ex1 frontend tests (lib/db.test.ts) are describe.skip'd because they test the old lib/db.ts contract against local JSON.

Why skipped, not deleted? They document the Ex1 data-access contract. Deleting them loses that documentation.

Fix: Ex3 first commit: un-skip and add fetch-mock (MSW or similar). Tests will still document the contract, now against the live API.

What's NOT a gap

  • CORS is env-configurable (fine for dev)
  • JWT expiry (60 min tokens, low risk for dev)
  • CV file serving from public/ (works for demo size)
  • No pagination (fine for 12 candidates; Ex4 will add if needed)
  • No audit log (deferred to Ex6, correct scope)
✓ Gaps are minor, known, and have a clear path. The exercise is submission-ready as-is. The gaps are honest scope boundaries, not problems.

Exercises 1–2 | Principles-First Orientation

The Thesis: I designed the architecture so the frontend doesn't know what technology the backend is. The data model is the contract; the storage is replaceable.

The Single Big Idea: The Seam

Exercise 1 reads candidate data from JSON files. Exercise 2 reads the same data from FastAPI+Postgres. The React UI code is identical in both.

Exercise 1: JSON Source

export async function getCandidates(): Promise { const data = await import('../data/candidates.json') return data.default.filter(c => c.status === 'Active') }

Exercise 2: FastAPI Source (Same Signature)

export async function getCandidates(token: string): Promise { const response = await fetch('/api/candidates', { headers: { Authorization: `Bearer ${token}` } }) return response.json() // Same shape }

The React Component (No Changes)

function CandidatesList() { const [candidates, setCandidates] = useState([]) useEffect(() => { getCandidates(token).then(setCandidates) }, [token]) return
{candidates.map(c => ...)}
} // This component works identically in both exercises. // It doesn't know or care where getCandidates reads from.
Result: Zero component changes. The data layer is a real boundary. The function signature (contract) doesn't change; only the implementation (body) does.

Why This Proves the Principle

If your architecture is right, you can swap entire technology stacks (JSON → Postgres, single server → distributed, sync → async) without refactoring consumers.

This is the difference between good architecture and "working code."

Why This Principle Matters (In Product)

1. Contracts Over Implementation

Your code depends on what data looks like, not where it comes from.

✓ Good

"Get me a Candidate with this shape"

Works with JSON, REST, GraphQL, gRPC. Survives technology rewrites.

✗ Bad

"Query the candidates table"

Breaks if you change backends. Requires refactor on every technology shift.

Product impact: You can experiment with different backends (serverless, cached, distributed) without touching product code. That's innovation velocity.

2. Data Model Mirrors Domain

Your schema doesn't optimize for UI convenience. It mirrors the domain.

Principle Example Why
Status is a pair property Application table (not on Candidate or Position) Abel is Rejected for job 1 but Waiting for job 3
Skills enable queries Normalized table (not JSONB) Ex4 needs "WHERE skill = 'Python'"
Order is preserved sort_order field Seeding is idempotent
Product impact: When requirements change (add filtering, search, export), the schema doesn't break. It was built for evolution.

3. Test the Contract, Not Implementation

✗ Brittle

"Test that the candidates list renders correctly"

Breaks when you change the DOM. Tests implementation.

✓ Robust

"Test that getCandidates() returns Active only"

Survives UI redesigns & backend swaps. Tests the contract.

Product impact: Tests document what the product guarantees, not how it's built. Those guarantees outlive implementations.

System Architecture

Three containers in docker-compose orchestrate the entire system:

Docker Compose Architecture (Interactive D2 Diagram)

Data Flow: Example Request

  1. Browser (React component): getCandidate(id, token)
  2. lib/db.ts: fetch('/api/candidates/cv_001', {Authorization: Bearer token})
  3. Vite proxy: forwards to localhost:8000
  4. FastAPI router: validates JWT → executes SQL
  5. SQLAlchemy: SELECT * FROM candidates ... JOIN candidate_skills ... JOIN candidate_experience ...
  6. Postgres: returns rows
  7. FastAPI: converts snake_case → camelCase via Pydantic
  8. Response: 200 {id, fullName, skills: [...], experience: [...]}
  9. Browser: setState(candidate) → re-render

Database Schema (11 Tables, Color-Coded)

All 11 Postgres tables visualized below with parent-child relationships. Color-coded by ownership: 🟧 Auth, 🟩 Candidates (5 sub-tables), 🟦 Positions (1 sub-table), 🟪 M:N Join (applications).

The Three Critical Design Decisions

🟩 1. Normalized Sub-tables (5 green under candidates)

Ex4 will need "WHERE skill = 'Python'" — impossible on JSONB. One extra JOIN per read is worth query capability that's essential for future features.

🟪 2. M:N Join Carries Status (purple, centered)

Status is a pair property. Abel McKinney is Rejected for job 1 but Waiting for job 3. Status lives on applications table, bridging candidates ↔ positions.

⏱️ 3. sort_order on Every Sub-table

Idempotent seeding: seed script can run 100 times and produce identical database. Without sort_order, insertion order is unstable across re-seeds.

The Three Key Decisions That Prove the Principle

1. String PKs Instead of UUIDs

Decision: Use existing IDs from source data (cv_001, job_001)

Why: Legacy data integration is simpler. No need for a mapping table.

The principle: The schema serves the data, not the framework.

2. Normalized Sub-tables Instead of JSONB

Decision: 11 separate tables (candidate_skills, candidate_experience, etc.)

Why: Exercise 4 will need `WHERE skill = 'Python'` or `WHERE start_year > 2020`. Those queries are impossible on JSONB but fast on normalized tables.

The principle: Design for future queries, not current convenience.

3. M:N Join Table with Status

Decision: Application table carries status (not Candidate or Position)

Why: Status is a property of the pair. Abel McKinney is Rejected for job 1 but Waiting for job 3.

The principle: Data model mirrors domain, not UI convenience.

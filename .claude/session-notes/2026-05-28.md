## Validation & Self-Check ✅

### Can I explain which fields were heuristic vs LLM-derived?

**Heuristic-only (regex, locked before LLM call):** email, phone, LinkedIn URL, GitHub URL.
**LLM-only:** full_name, headline, skills, experience, education, certifications, languages, summary.
**Conflict resolution:** silent dict merge — `{**llm_dict, **hint_overrides}`. Heuristics win, no warning emitted (override is intentional, so no signal degradation).

### If the LLM fails or returns nonsense, do I notice?

Three-tier failure taxonomy:
- **Malformed JSON or missing `full_name`** → `ValidationError` → orchestrator catches → `FAILED` result → HTTP 422. `extraction_runs` row written with `status=failed`, `errors[]` populated, `entity_id=null`.
- **Type mismatch on optional field** (e.g. `start_year: "2019"`) → cast attempt + warning → `PARTIAL` + HTTP 201. `extraction_runs` row written with `status=partial`, `warnings[]` populated, `entity_id` set.
- **ParseError / BedrockError** → propagates to endpoint → HTTP 422. `extraction_runs` NOT written (pipeline never started / LLM call failed entirely).

Every failure path is observable via `extraction_runs`. Replay any run: `SELECT prompt_text, raw_llm_output FROM extraction_runs WHERE id = X`.

### Would I trust this summary to represent the candidate to a recruiter?

For Adeline Cordova (`SUCCESS`, no warnings): conditionally yes.
- **Got right:** 12 skills (alphabetical), 3 experience entries (correct date order), summary matches CV prose, heuristic-locked email/phone match source.

### Double-ingest test — same document twice

**Finding: non-deterministic LLM behaviour caught by observability layer.**

Run 1 (success): LLM returned clean JSON → `input_tokens=834, output_tokens=556, status=success`
Run 2 (failed): LLM returned ` ```json\n{...}` ` (markdown-fenced) despite prompt saying "No markdown fences" → `json.loads()` fails at char 0 → `status=failed, entity_id=null`

The underlying data in run 2 was correct (same fields, same values), but wrapped in a code fence the validator couldn't parse. Both runs are in `extraction_runs` — the failure is auditable and replayable.

**What this teaches:**
1. LLM instruction-following is probabilistic — the same prompt on the same document can produce different formatting
2. The validator's `json.loads()` is a strict gate; markdown fences fail it immediately
3. The observability layer (unconditional `extraction_runs` write) caught this perfectly — raw output is preserved
4. The practical fix: strip ` ```json` / ` ``` ` fences in the validator before `json.loads()` (a one-line pre-processing step). This is a known Nova Lite quirk.

## Demo / Show-and-Tell Reference

**Which parts of the document were hardest to extract reliably?**
Experience date ranges in varied formats ("March 2019 – Present", "2019-present", "present"). The prompt instructs: "Present/current as end_year → omit the field (null)". The LLM follows this inconsistently — sometimes returns `null`, sometimes omits the key, sometimes returns the string "present". The validator handles these as PARTIAL warnings. Skills in Hebrew or mixed-language CVs are also fragile.

**Where did heuristics outperform the LLM?**
Email and phone: regex is 100% accurate by definition. In run 2's raw output, the LLM returned `"email": "adeline.cordova@email.com"` correctly — but heuristics had already locked it in before the LLM call. If the LLM had hallucinated or reformatted the address, the regex value would have won silently.

**How would errors here affect later ranking and search (Ex4/Ex5)?**
- Missing skills → candidate excluded from skill-based search queries entirely
- Wrong start_year → experience ranking broken (sorting by seniority uses startYear)
- Empty summary → embedding vector is zero-information (Ex5 vector search returns random matches for that candidate)
- PARTIAL records need human review before being included in ranked results; ideally filtered out of automated ranking
